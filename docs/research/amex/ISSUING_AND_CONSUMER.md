# American Express issuing, account controls and consumer experience

Research date: 2026-09-08. This is a public-evidence design study, not a reconstruction of Amex's private architecture. Twenty-one useful primary sources were opened and read. The [source register](issuing-sources.json) records product, geography, evidence and access limitations. Sources are predominantly U.S.; the Canadian mobile tutorial is explicitly comparative. Undated pages were observed on the research date, which does not establish their last revision date. No authenticated Amex portal, live application, account, card or transaction was used.

## What the reference actually supports

The useful target is recognizable task behavior: clear account context, separated responsibilities, one durable request, understandable controls, transaction detail, statements, payment scheduling, reliable status and helpful recovery. “90%+” must be measured against a defined observable task catalog. These documents alone cannot prove internal architectural similarity, production service quality or 90% implementation completion.

## Proposed Etail workflows

Everything below is an Etail design proposal constrained by [ACCESS_POLICY](../../ACCESS_POLICY.md), [WORKFLOWS](../../WORKFLOWS.md) and [UX_CONTRACT](../../UX_CONTRACT.md). State names and database boundaries are our engineering choices. They are not claims about Amex's source or production internals.

| Task | Actors, steps and states | Required exceptions and recovery |
|---|---|---|
| Add an additional/employee card | Eligible owner or explicitly authorized issuer selects account → existing/eligible holder → format and controls → review → submit canonical request. Keep `DRAFT/BLOCKED/READY/SUBMITTED/PROCESSING/ISSUED/DECLINED/NEEDS_REVIEW`. | Duplicate retry returns the same operation; stale draft reports version conflict; revoked invitation blocks submission; timeout remains processing; holder cannot issue merely because they can spend. |
| Assisted application and approval | Requester saves; required applicant contribution or independent reviewer completes a scoped task; approval binds exact payload and version; issuer outcome follows separately. | Approver absence routes to an authorized queue; expired invitation offers a controlled renewal; modified payload invalidates old approval; decline preserves explanation/history. Never give every manager an override. |
| Activation and first use | Issued card with activation requirement → actor authorized by the applicable holder/guardian/product policy performs supported verification → activation command → active or pending/help. | Guardian activation behavior must be resolved for supervised participants without a login. Already activated is idempotent; wrong card scope fails; delivery alone cannot imply activation; no PAN/PIN is collected by the sandbox. Future reveal/PIN is provider-hosted and step-up protected. |
| Freeze and unfreeze | Select card → show exact effect and governing parent restriction → confirm → command pending → effective freeze status and actor. | Child unfreeze cannot defeat account/guardian freeze; a failed adapter update must not show effective success; late clearing still reconciles. |
| Replace | Card detail → reason → permitted delivery/format choices → review old-card effect → same request engine with replacement kind → processing/issued/fulfilled as separate facts. | Compromise must not offer unsafe number reuse; returned shipment is not completed delivery; retry cannot create another replacement; balances, limits and rewards do not reset. |
| Edit controls | Owner or delegated controller sees period, committed usage, ceiling and enforcement type → new value → review impact → atomic command. | Raising a card ceiling cannot create backing; lowering below exposure needs explicit permitted behavior; two concurrent spends cannot oversubscribe shared capacity; merchant-category alert never becomes an unsupported hard block. |
| Read activity and statement | Account/holder filter → pending/posted distinction → transaction detail → source-linked refund/dispute/receipt → period statement or export. | Read permissions apply to search, totals, export, files and direct URLs; archived retrieval shows pending; empty data differs from unavailable data. |
| Repay or schedule | Responsible authorized actor reviews target obligation, source, amount semantics and date → confirms → scheduled/processing/applied/failed/returned. | Recheck outstanding amount and authority at execution; manual payment racing schedule follows one defined policy; cancellation race reports durable outcome; returned payment restores only the actual reversed financial effect. |
| Report a problem | Transaction detail → recognize merchant/duplicate/pending/fraud question → fraud safety route or posted dispute → reason and evidence → submitted case → next step/status. | Pending fraud can be reported without claiming a formal chargeback; original refund is checked; withdrawal and later evidence remain auditable; provisional financial effect differs from final resolution. |
| Security recovery | User selects purpose-bound recovery → verified challenge → session/device change → confirmation and audit. | Expired/replayed challenge fails; resend is throttled; safe fallback remains; removing a device revokes its authority; support identity verification cannot grant payout permission. |
| Alerts and preferences | Choose account/card, event and delivery channel → verify destination/permission → save → show active settings. | Delivery failure does not change financial status; mandatory security messages are distinguished from optional notices; revoked delegates stop receiving scoped content; lock-screen content minimizes sensitive details. |
| Rewards and benefits | Person-level summary → source-account details and rule explanation → eligible benefit enrollment/redemption where specified → durable pending/result. | Shared Premier cap remains shared across cards/accounts; refund corrections reference original accrual; no browser-derived eligibility; no fabricated Amex travel/concierge/offers product. |

## Architecture implications and operator work

Retain the modular monolith and one financial ledger. Model person, typed account, responsible party, grant, holder assignment, backing facility, card request, provider operation and card separately. Corporate control-account hierarchies are useful as organizational scope references; they do not create a fourth Etail customer account type.

Use one command boundary for every customer and authorized operator action. The application/approval module owns drafts and immutable submitted snapshots. The issuing module owns card lifecycle and capacity decisions. Activity/statement projections explain ledger events; they do not mutate balances. The case module links inquiries, evidence and decisions to original transactions. Notifications announce durable facts through an outbox. These boundaries support the observed behaviors without asserting that Amex uses this architecture.

An operational work queue should show task, account, age, next deadline, responsible team, blocked reason and permitted next action. Provide distinct queues for applications awaiting information, provider outcomes needing reconciliation, delivery exceptions, returned repayments, disputes, reward corrections and failed notifications. Support can inspect an authorized case and collect evidence; finance adjustments require separate authority and correcting entries. Every override records scope, reason, evidence and approval. UI must never turn “request sent” into “card issued,” “payment applied,” or “case won.”

## Acceptance scenarios for the parity catalog

These are proposed tests, not executed results.

1. An invited holder resumes the same request after session expiry with the intended account intact.
2. Two submission clicks and a transport timeout produce one issuance business effect.
3. Changing holder or limits after approval invalidates approval before submission.
4. A manager without issuance capability can perform permitted reporting but cannot add a card.
5. A cardholder can inspect own activity without receiving unrelated Personal or Seller totals.
6. An expired/revoked invitation cannot be accepted from an old tab.
7. Card activation cannot bypass the holder/account relationship.
8. A replacement keeps historical activity and leaves shared capacity usage unchanged.
9. A parent freeze remains effective after an attempted child unfreeze.
10. An unconfirmed provider freeze is visibly pending or failed, never silently active.
11. A genuine delayed clearing arriving after freeze updates financial records exactly once.
12. A limit edit cannot reset already committed period usage.
13. An alert-only category rule is labeled as an alert and is tested separately from hard restriction.
14. Statement, export and attachment access enforce the same scope as on-screen activity.
15. An archived statement request survives refresh and has a recoverable failure state.
16. AutoPay enrollment explains whether the currently due obligation is included.
17. Manual repayment and scheduled execution cannot silently duplicate an intended payment.
18. Cancel racing settlement returns the authoritative final result.
19. A returned repayment has an explicit status and correcting financial effect.
20. A customer can report suspicious pending activity without an invented chargeback outcome.
21. A dispute/refund race cannot reimburse the same amount twice.
22. Notification retries create no second transaction, reward or application.
23. A revoked manager cannot fetch the account through a stale notification or export link.
24. A reward reversal preserves original membership year and shared-cap attribution.
25. Keyboard and screen-reader users can review, submit, locate pending status and read the statement without help.

## Evidence gaps and deliberate departures

- Private Amex underwriting, risk models, ledger schema, authorization latency, staff permissions and escalation SLAs were not inspected. Public descriptions establish behavior examples, not guaranteed coverage of every product.
- The linked GAFC “on behalf of” PDF was publicly reachable but explicitly marked proprietary/confidential. It was excluded from substantive design reuse and is recorded as an excluded source. Public FAQs provide the needed applicant/admin concepts.
- The U.K. activation page and attempted U.S. mobile/terms pages failed to open. A card-offers FAQ returned a JavaScript shell; search snippets alone were not promoted to verified page evidence.
- Some sources are stale or undated. In particular, the rewards FAQ retains COVID-era content. Use its vocabulary as a reference; verify governing current product terms before implementing any corresponding commercial policy.
- Etail's guardian funding, Personal privacy, explicit grants, exact money, backed capacity, shared Premier cap and immutable financial corrections remain normative. No Amex age, annual fee, interest, points rate, grace period, credit-bureau rule, automatic unfreeze, or travel entitlement is imported.
- Hosted identity lifecycle, physical delivery, provider-backed PIN/reveal, wallet provisioning and production repayment/chargeback access remain separate implementation/integration work. This study does not enable them or claim their completion.
