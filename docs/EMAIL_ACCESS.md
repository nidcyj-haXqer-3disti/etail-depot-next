# Email access — local implementation

The local app supports creating a login, email confirmation, password sign-in, and password recovery against the recorded new Netlify Identity provider. Sample-user buttons remain a separate way to explore fictional services. An email address never selects a sample identity or grants access to its data.

## Current provider and runtime

The provider is `https://etail-depot-next.netlify.app/.netlify/identity`, bound to site `cbbb6c24-9dbc-43a2-9234-e4357b5b5280` in `project-targets.json`. The coordinating agent then changed only the owned site's email-verification setting: the subsequent read showed `autoconfirm:false`, `disable_signup:false`, and `external.email:true`. Registration remains open; no users, credentials, sender settings, or privileges were changed by this work. No registration or recovery email was sent by the agent.

Runtime password commands require explicit `APP_ENV=local`, an explicit loopback `ETAIL_PUBLIC_ORIGIN`, and no CI/Netlify runtime indicators. They contact only the recorded HTTPS issuer. The preview process needs network access to that issuer. Test/hosted environments cannot enable this path merely by setting a readiness flag. Public rollout, hosted session lifecycle integration, and deployment remain separately gated.

## First-time use

1. Open the local `/login` page and choose **Create a login**. Enter an email address you control and a password of at least 12 characters.
2. Check your inbox. New registration requires confirmation; a recognized already-registered response has the same neutral public result and suggests signing in instead.
3. For the local preview, open the email link and copy the **final Etail Depot page address** into **Confirmation link**. This accommodates email link tracking and Netlify's own-site redirect restriction. Do not paste the link into chat or share it with another person.
4. Confirm, then sign in with the email and password. Confirmation does not automatically switch the browser into an identity.

The public root page and `/login` also recognize normal confirmation/recovery fragments. They remove the fragment, retain its parsed token only in memory, and use the same form. The root handoff survives client navigation without putting the token in a query string, cookie, local storage, or session storage. An invalid callback gets an explicit error. Hosted command enablement still requires its separate release gate; callback code alone does not enable a deployment.

**Forgot your password?** requests recovery with a neutral response. The reset form accepts the final recovery link and a new password. A successful reset revokes existing application sessions before changing the provider password and requires a new sign-in. If a link fails before a password update is dispatched, request a new recovery email. If a dispatched password update has an uncertain outcome, the affected identity stays blocked and requires owner-assisted review; ordinary sign-in and another reset cannot remove that block. Email delivery and a real user-owned mailbox roundtrip have not been verified by the agent.

## Identity and session boundaries

- The adapter uses the required `@netlify/identity` configuration discovery. Its documented provider exchanges stay server-side because the SDK's normal browser session flow uses browser-readable provider cookies. Only verified provider issuer/subject reaches identity binding; provider tokens are discarded and never returned to the client.
- `providerConfirmed` means the provider reports confirmation. It is not KYC, service eligibility, or independent proof that an older automatically confirmed address was ever mailbox-verified. New registrations require confirmation settings and reject an unexpected automatically confirmed signup response.
- Binding creates an identity/person only. It grants no service membership, card, merchant assignment, operator access, or fictional eligibility. Real-login service enrollment is not implemented by this authentication change.
- Only password sign-in issues the existing opaque HttpOnly, SameSite=Strict app session. Confirmation/recovery endpoints return minimal results with no app cookie. Provider errors, passwords, link tokens, and personal details are not logged or echoed.
- Exact-origin checks and strict bounded JSON apply to every mutation. Persistent hashed attempt counters allow at most ten attempts per normalized login bucket in 15 minutes and sixty shared attempts per minute. Counter data contains no raw email or password. Old counters are cleaned after 24 hours.
- One nonblocking PostgreSQL advisory boundary serializes local password verification through app-session issuance against recovery verification, session revocation, and password update. Concurrent attempts receive `AUTHENTICATION_BUSY` and must retry. This avoids holding waiting auth connections that could exhaust the pool. The lock alone cannot establish whether a timed-out provider update later committed.
- The durable `identity_password_resets` barrier addresses that ambiguity. Before dispatching a password update, the session repository locks the exact identity binding, records `RESET_PENDING` with a fresh attempt ID, and revokes its sessions in one committed transaction. Session insertion and rotation check this marker under the same binding lock. Only a definitive successful provider response for the exact attempt permits final revocation and `COMPLETE`. A timeout, malformed result, process interruption or uncertain write leaves the barrier in place. Other identity bindings remain unaffected, even for the same Person.
- An unresolved attempt cannot be replaced or cleared by another reset, a successful password verification, elapsed time or a flag. The UI directs the user to the person running the preview. There is no automated owner-reconciliation endpoint in this change: restoring that identity requires evidence that the outstanding provider write has reached a definitive outcome and a separately reviewed recovery procedure. Do not delete the marker to manufacture a completed recovery. The ordinary first-attempt successful reset remains usable.
