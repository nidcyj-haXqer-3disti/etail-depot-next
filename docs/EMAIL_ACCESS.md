# Email access — local and canonical hosted implementation

The app supports creating a login, email confirmation, password sign-in, and password recovery against the recorded new Netlify Identity provider. The explicit local preview and the approved canonical production deployment use the same provider adapter and application session owner. Sample-user buttons remain local-only. An email address never selects a sample identity or grants access to its data. Deployment receipts and production acceptance are recorded separately; code enablement alone does not prove a deployed runtime or mailbox delivery.

Local password commands require explicit `APP_ENV=local`, an explicit loopback `ETAIL_PUBLIC_ORIGIN`, and no CI/Netlify runtime indicators. They contact only the recorded HTTPS issuer. The preview process needs network access to that issuer.

The approved hosted path requires `APP_ENV=production`, exact recorded `SITE_ID`, exact canonical `ETAIL_PUBLIC_ORIGIN`, `ENABLE_REAL_MONEY=false`, and `ENABLE_LOCAL_FIXTURE_IDENTITY=false`. It also calls `getContext()` from the pinned `@netlify/functions`6.0.0 SDK and requires the **actual current request's** site ID to match and its deployment context to be `production`. Function runtime `CI` must be absent or `false`; CI builds do not authenticate. Missing request context, local/test app environment on Netlify, a branch/deploy-preview request, unrelated origin or site, or enabled fixture/real-money flag rejects email commands. There is no environment-controlled readiness bypass.

The first hosted candidate incorrectly required `NETLIFY` and `CONTEXT` as runtime environment variables. Official Netlify documentation lists those as build metadata; only `URL`, `SITE_NAME` and `SITE_ID` are guaranteed read-only Function variables. The corrected factory uses the request-context API instead of manually setting reserved variables or trusting a copied production label. The compiled Next function retains dynamic environment reads; no build-time substitution was responsible. See [Functions environment variables](https://docs.netlify.com/build/functions/environment-variables/), [build environment variables](https://docs.netlify.com/build/configure-builds/environment-variables/), and [Functions API](https://docs.netlify.com/build/functions/api/).

The Identity adapter separately obtains the actual issuer with `@netlify/identity` on each operation and requires its URL to match. The SDK resolves its server context or Netlify's `URL`; a `NETLIFY_IDENTITY_URL` variable alone does not satisfy this check.

Hosted sessions and throttling require the fresh site-owned Netlify Database branch and all five current migrations, including `password_login_throttle` and `identity_password_resets`. Public requests never migrate or seed it. The production database uses the provider-managed `NETLIFY_DB_URL`; a local preview URL or copied fixture data is not permitted.

## First-time use

1. Open `/login` and choose **Create a login**. Enter an email address you control and a password of at least 12 characters.
2. Check your inbox. New registration requires confirmation; a recognized already-registered response has the same neutral public result and suggests signing in instead. Creating a login again does not change an existing password. Use password recovery when needed; a duplicate registration does not prove another email was sent.
3. On the hosted site, open the email link and continue on the confirmation form it opens. The parsed link is kept in memory and no extra paste is required. For the local preview, complete confirmation in the canonical site tab opened by the email, then return to the local preview to sign in. The address bar is deliberately cleared of the link code; copying that final address cannot complete confirmation. The optional paste field accepts only a supported link that still contains its original code. Do not paste the link into chat or share it with another person.
4. Confirm, then sign in with the email and password. Confirmation does not automatically switch the browser into an identity.

The public root page and `/login` recognize normal confirmation/recovery fragments. They remove the fragment, retain its parsed token only in memory, and use the same form. The root handoff survives client navigation without putting the token in a query string, cookie, local storage, or session storage. An invalid callback gets an explicit error. A reload after consuming the in-memory link requires opening the email link again; no credential is persisted to avoid that extra step.

**Forgot your password?** requests recovery with a neutral response. Open the latest recovery email and complete the new-password form in the tab it opens. The optional paste field requires the original link code, not the cleaned address bar. A successful reset revokes existing application sessions before changing the provider password and requires a new sign-in. If a link fails before a password update is dispatched, request a new recovery email. If a dispatched password update has an uncertain outcome, the affected identity stays blocked and requires owner-assisted review; ordinary sign-in and another reset cannot remove that block. Email delivery and a real user-owned mailbox roundtrip have not been verified by the agent.

## Identity and session boundaries

- The adapter uses the required `@netlify/identity` configuration discovery. Its documented provider exchanges stay server-side because the SDK's normal browser session flow uses browser-readable provider cookies. Only verified provider issuer/subject reaches identity binding; provider tokens are discarded and never returned to the client.
- `providerConfirmed` means the provider reports confirmation. It is not KYC, service eligibility, or independent proof that an older automatically confirmed address was ever mailbox-verified. New registrations require confirmation settings and reject an unexpected automatically confirmed signup response.
- Binding creates an identity/person only. It grants no service membership, card, merchant assignment, operator access, or fictional eligibility. After authentication, the separate hosted sandbox participation and service-enrollment commands require explicit member action; authentication does not grant them automatically.
- Only password sign-in issues the existing opaque HttpOnly, SameSite=Strict app session. On HTTPS it uses the `__Host-etail_session` name, `Secure`, root path, and no Domain attribute. Confirmation/recovery endpoints return minimal results with no app cookie. Provider errors, passwords, link tokens, and personal details are not logged or echoed.
- Exact-origin checks and strict bounded JSON apply to every mutation. Persistent hashed attempt counters allow at most ten attempts per normalized login bucket in 15 minutes and sixty shared attempts per minute. Counter data contains no raw email or password. Old counters are cleaned after 24 hours.
- One nonblocking PostgreSQL advisory boundary serializes password verification through app-session issuance against recovery verification, session revocation, and password update across application instances sharing the database. Concurrent attempts receive `AUTHENTICATION_BUSY` and must retry. This avoids holding waiting auth connections that could exhaust the pool. The lock alone cannot establish whether a timed-out provider update later committed.
- The durable `identity_password_resets` barrier addresses that ambiguity. Before dispatching a password update, the session repository locks the exact identity binding, records `RESET_PENDING` with a fresh attempt ID, and revokes its sessions in one committed transaction. Session insertion and rotation check this marker under the same binding lock. Only a definitive successful provider response for the exact attempt permits final revocation and `COMPLETE`. A timeout, malformed result, process interruption or uncertain write leaves the barrier in place. Other identity bindings remain unaffected, even for the same Person.
- An unresolved attempt cannot be replaced or cleared by another reset, a successful password verification, elapsed time or a flag. The UI directs the user to the site owner. There is no automated owner-reconciliation endpoint in this change: restoring that identity requires evidence that the outstanding provider write has reached a definitive outcome and a separately reviewed recovery procedure. Do not delete the marker to manufacture a completed recovery. The ordinary first-attempt successful reset remains usable.

## Session lifetime and remaining hosted scope

Application sessions have an absolute eight-hour maximum. Rotation preserves the original expiry. App sign-out, other-session revocation, and password resets through these app endpoints revoke the relevant sessions. A provider-side deletion, password change, email change or administrative action performed outside these endpoints does **not** immediately revoke an existing application session; it can remain valid until its original expiry or an explicit application revocation. No Identity lifecycle webhook, provider status polling or universal instant revocation is claimed by this release.

Creating and confirming an email login is independent from service enrollment. A newly bound person has no service membership, card, merchant assignment, eligibility or operator privileges. D60 added explicit hosted sandbox participation and service enrollment. Those commands remain separate from authentication, and authentication acceptance alone does not establish the card or merchant journey. See [hosted sandbox product](HOSTED_SANDBOX_PRODUCT.md).
