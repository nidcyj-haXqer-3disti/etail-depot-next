# D70 — confirmation waits for its saved review

12 September 2026. Follow-up to the reported GitHub exit code 1 on PR14. D69 remains the product and money-model contract.

GitHub run `34639215532`, job `103398098682`, failed on application head `187b5a3b9ad747ef074ee8b9406ec8eabf05f5fe`. Its preceding lint, typecheck, 389 unit, 208 integration, 39 concurrency, 12 contracts, architecture, production build and 9 API checks passed. Of 140 desktop/mobile cases, 139 passed; the desktop lost-checkout-review recovery case did not reach Payment complete. Later accessibility/security/handoff steps were skipped, so that run is failed evidence. The focused diagnostic is retained in `artifacts/d70-ci-failure.log`.

The cause was a customer-visible navigation race. Preparing a review immediately rendered the Pay button while a server request was still replacing the page with its durable review URL. That replacement changes the component key. A quick confirmation could run in the preceding component, then be replaced by the earlier unpaid server projection. Add money used the same key-change pattern and could lose the visible confirmation/recovery owner in the same way. This was not fixed by increasing test timeouts or adding automatic retries.

Both flows now mark saved-review navigation as a React transition. Their confirmation handlers and controls stay blocked while that transition is pending. The exact review-key boundary, server eligibility, financial commands, immutable request identities, privacy behavior and ledger rules remain unchanged. Funding's Change amount link also stays unavailable during the transition.

Two deterministic browser regressions obtain a real saved-review response and hold its delivery. They prove confirmation is disabled and has no financial effect before releasing that response. The checkout case then proves one payment/debit with a durable receipt after reload; the funding case loses the actual committed confirmation response, retries the same intent and proves one top-up, one journal and balanced entries. Both tests failed at the expected disabled-control assertion against the preceding production build. Logs: `artifacts/d70-checkout-before.log` and `artifacts/d70-funding-before.log`.

The corrected production build passes 18 targeted desktop/mobile/accessibility cases, including both new regressions, the originally failed case, malformed/denied recovery, spending-limit recovery and the connected funding→purchase→refund→deposit journey. `artifacts/d70-regressions.log` records the complete 18/18 run with no test retries. Types, lint, architecture, source security and production Next/offline Netlify packaging pass in the corresponding `artifacts/d70-*.log` files. No database migration, dependency, hosted setting or live-money behavior changed.

Independent review confirmed that command identity, access-denial recovery and the review-key boundary are preserved. A separate pre-existing cross-panel limitation remains: a spending-limit attempt can overlap top-up navigation, whose workspace replacement can discard that limit's local recovery state. This correction covers checkout and top-up confirmations; it does not certify mutual exclusion between every command on the funding screen.
