# Public evidence of Amex payments, fraud and data architecture

Research date: 2026-09-08. This supplements [the Etail architecture proposal](ARCHITECTURE_AND_MANAGEMENT.md), [issuing research](ISSUING_AND_CONSUMER.md) and [merchant research](MERCHANT_AND_OPERATIONS.md). It examines publicly disclosed components and engineering decisions. It is not a reconstruction of the complete private Amex system.

The strongest findings are a deployed recurrent-model fraud inference stack, a firsthand account of the enterprise Hadoop platform, Amex-coauthored graph-learning research, an exact published preprocessing method, and a real Amex open-source scheduler. They justify learning from Amex's separation of financial commands, data processing and specialist computation. They do not justify buying every vendor in an Amex customer list or replacing Etail's required PostgreSQL modular monolith.

### The recurrent-model discrepancy matters

T01 and T02 corroborate the serving components but disagree about the recurrent cell. Describe this as **a recurrent-model fraud inference stack**, preserving both labels in the evidence. Neither source gives enough detail to reconcile the discrepancy. Likewise, the reported latency/performance applies to the described subsystem and historical hardware comparison; it cannot become Etail's end-to-end payment SLA or a 2026 Amex benchmark. We did not run the models or independently reproduce vendor results.

## What data flows are actually disclosed

These compact flows summarize the cited public descriptions; they are not copied private diagrams. Arrows connecting separately disclosed components beyond a source's explicit scope would be inference, and are omitted.

**Fraud model lifecycle, T01/T02:** training on historical data → optimized model artifact → accelerated inference service → fraud output. The publications do not identify the upstream operational database, queue, deployment approval system, financial posting engine, or fallback when inference times out.

**Research preprocessing, T04/T05:** input series → outlier mitigation → shift → scale → power transformation → neural network. The paper distinguishes global/local normalization and a separate EDAIN-KL variant. This is a model-layer architecture, not an issuer platform. The article's figure caption and paper equations were read; image fetch did not succeed, so no pixel-level diagram inspection is claimed.

**Open-source scheduler, T07:** scheduled work → interval bucket → throughput selection and overflow → interval runner → caller-supplied executor. Peer discovery adjusts shared throughput. Timing can be early or delayed within documented scheduling constraints; this is not a bank cutoff-time scheduler or a durable transaction log. The linked diagram image could not be fetched; the README's nine-step explanation was read.

For payment network cells and ISO 8583 connection migration, use the separately researched Amex engineering disclosures in the architecture synthesis. For customer remittances and payment-hub integration, use the provider evidence in the merchant/operations research. Card purchase authorization, customer bill repayment and merchant settlement are different workloads even when a vendor calls all of them “payments.”

## Etail implications: proposed, not observed Amex internals

1. **Keep financial authority in the existing domain and ledger.** A future risk score is input to the one policy/authorization command. It must not independently create a card, change a limit, post a journal or override guardian funding. For the current sandbox, use explicit deterministic mock decisions through the same interfaces.
2. **Separate the decision record from the model runtime.** Design a versioned assessment record containing purpose, scoped resource, permitted feature-set version, as-of time, model/rule version, correlation ID, result category, safe explanation and latency. Store only needed references or redacted data. Exact schemas remain implementation work; no new database is selected here.
3. **Make uncertainty an operating state.** Distinguish allow, explicit decline, challenge/review, dependency timeout, stale input and invalid output. The authorized product policy must determine handling; a missing model result must not silently grant spending. Reconcile any upstream operation whose outcome is unknown before retrying it.
4. **Use one PostgreSQL source of financial truth, with scoped derived views.** Start reporting and operational queues with database projections and durable outbox/inbox work. Add caching, a separate analytics store or specialized computation only after a measured bottleneck and isolation review. No Hadoop, Kafka, Cassandra, Redis or GPU deployment is implied by this research.
5. **Treat model delivery as controlled software delivery.** Any later model needs frozen feature definitions, time-aware evaluation, false-decline and missed-fraud assessment, resource-specific rollout, monitoring, rollback and a tested fallback. Retraining should be separate from card authorization. Data-quality checks and reversible deployments are useful even before ML exists.
6. **Provide observable customer and staff recovery.** A fraud assessment, customer notification, challenge, case, provider action and financial effect need distinct records and statuses. Delivery failure must reach an operations queue. An operator resolves cases with scoped commands rather than editing a score or balance.

The research repositories are **study references**. T06's unresolved license and dataset permissions preclude treating its code/data as ready for reuse. T07 is a Java library with timing and durability limits, outside the current TypeScript application choice. We have not installed, executed, imported or security-audited either project.

## Acceptance scenarios to add when the relevant slice is built

| Scenario | Required Etail outcome |
|---|---|
| Fraud dependency times out during a command | Explicit uncertain/timeout outcome; no automatic approval, false completion or duplicate financial effect. |
| A feature projection is older than the allowed cutoff | Staleness is detected and handled by product policy; record the data version used. |
| A score is `NaN`, infinite, malformed or outside its declared range | Reject the provider result, record a safe exception and use the defined recovery path. |
| Model deployment changes during a retry | The decision record identifies the version used; retry reconciliation prevents a second effect. |
| One household member's history is requested through another context | The server denies the unauthorized read regardless of model usefulness. |
| A favorable score conflicts with a frozen card or insufficient backing | Existing card/policy/backing constraints prevail atomically. |
| Fraud is reported after clearing or after a replacement | Preserve the original transaction/instrument chain; open the appropriate case and reconcile any monetary correction. |
| Historical events are replayed for a report | Rebuild the derived result without resending customer notifications, reissuing cards or reposting money. |
| Customer alert delivery fails | Financial state remains explicit; staff can see and retry the communication safely. |
| A copied vendor diagram includes a database next to an Amex logo | Evidence review rejects the deployment claim unless its Amex-specific provenance and date are established. |

These are proposed validation cases, not executed tests or a claim that 90% of Amex architecture has been reproduced. Public workflow parity and resilience requirements can be measured in Etail; completeness against Amex's undisclosed internals cannot.
